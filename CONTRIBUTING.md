# Contributing

Thank you for improving the Source-Aware Intelligence Hub.

## Before changing code

1. Read `AGENTS.md`, `CLAUDE.md`, and the relevant document under `docs/`.
2. Keep the product credential-free, deterministic, synthetic, and read-only.
3. Open an issue for a material contract, dependency, or architecture change.
4. Work in a focused branch with one writer per mutable worktree.

## Development loop

Add a failing behavior test first, run it to confirm the expected failure, make the smallest production change, then run focused and governing checks. Preserve explicit unavailable and conflicting states; never convert missing evidence into a healthy default.

Run every command in the README verification block before requesting review. A change is not ready while a formatter, lint, type, test, build, dependency, privacy, history, accessibility, or runtime gate fails.

## Public-safety rules

Use fictional names and records only. Do not commit credentials, real account payloads, personal or client context, private infrastructure details, local paths, network topology, operational logs, screenshots from private systems, generated caches, or copied history. Do not weaken scanner patterns or exclusions merely to make a gate pass.

## Pull requests

Explain the user outcome, changed contracts, RED/GREEN evidence, security and accessibility impact, exact verification commands, and residual limitations. Keep unrelated changes separate. Reviewers may require a fresh exact-candidate scan and browser smoke.
